## What was built

- `browser-engine`: `Engine` trait, `EngineEvent` stream, and a macOS adapter
  that creates a real `WKWebView`, attaches it to GPUI's AppKit content view,
  applies navigation policy, forwards navigation lifecycle events, supports
  back/forward/reload/stop, JS evaluation, zoom, visibility, JSON expression
  evaluation, PNG snapshots, popup/external-scheme requests, media-capture
  denial, and web-process termination events.
- `browser-testserver`: deterministic loopback HTTP fixtures (HTML/CSS/JS,
  redirects, downloads, slow pages, 404s).
- `m0-probe`: an automated harness that opens a real GPUI window, embeds real web
  views, and asserts behaviour, writing `target/m0-report.json`.
- `scripts/m0-probe.sh`: runs the probe and samples host and WebKit helper RSS.

## Measured resources (debug build, probe workload)

Probe workload: real HTTPS site + local page with JS/CSS, then a second web
view, snapshot, resize.

| Metric | Value |
| --- | --- |
| Peak host (GPUI + WebKit UI process) RSS | ~165 MB |
| Peak WebKit helper RSS (GPU + WebContent ×2 + Networking) | ~151 MB |
| Peak total | ~316 MB |
| WebContent process per simple page | ~30 MB |
| GPU helper | ~30 MB |
| Networking helper | ~16 MB |
| Probe binary (debug) | ~8 MB |

Notes:

- These are debug-build numbers under a probe that intentionally creates two
  views. Release and steady-state measurements belong to M6.
- WebKit helper processes are XPC services (parent is `launchd`), so the harness
  identifies them as WebKit processes that did not exist before launch. Measure
  on an idle machine.
- Helper memory is separate from GPUI overhead, as required.

## Platform findings / limitations

1. **Overlays**: GPUI cannot draw above the native web view. Mitigation policy in
   ADR-0003 (full-page surfaces hide the page; native menus; popup windows).
2. **Keyboard shortcuts**: while WebKit is first responder, GPUI's key handling
   does not receive keys. A local `NSEvent` monitor will forward browser
   shortcuts (Phase 1).
3. **Engine**: WebKit = Safari engine. No Chromium-grade site-isolation claims;
   WebKit process-per-view is used, and process termination is surfaced.
4. **Favicons**: no WKWebView API; browser must fetch/infer them.
5. **DevTools**: available through `isInspectable` on macOS 13.3+ (debug builds
   enable it); not yet exposed in the UI.
6. **Downloads/popups/permissions**: policy hooks exist (delegate + events);
   user-facing flows are Phase 3/5 work.
7. **Automated visual verification of GPUI chrome** is not possible in this
   environment (no screen-recording permission; GPUI exposes no capture API).
   Chrome is verified behaviourally and via the manual checklist; page pixels are
   verified with WKWebView snapshots.

## Decision

Proceed with the architecture: GPUI chrome + direct WKWebView native subviews,
engine boundary as designed. Start Phase 1 (browser foundation).
